The private mesh is both a capability feature and a performance feature. A small device can borrow a warm model from a paired device instead of loading it locally, and a saturated desktop can shed overflow to a paired peer.

Public cells are a separate untrusted discovery surface. Opted-in providers publish signed,
short-lived QVAC capabilities there. An explicit public or eligible automatic route dials a
dedicated Noise-authenticated transport, streams a job with a unique replay-protected id, and never
adds the provider to the private mesh. Only the job payload crosses that boundary.

## Route by capability and sensitivity

The Conductor ranks live route options from local QVAC inventory and Hypha's peer view. A route option includes tier, alias, tags, price, inflight count, mesh id, and peer key.

The ranking obeys two constraints:

| Constraint | Behavior |
| --- | --- |
| Capability | Pick a model that matches the required modality, size class, and specialist tag. |
| Sensitivity | Private turns remain local or inside the paired mesh. Only explicitly shareable jobs may use public providers. |

Quick trivial text turns stay local. Private memory, files, health, credentials, and device-specific context require a local or private mesh route.

## How Leash chooses a peer

The model first supplies a capability bar, not a hostname. Deterministic code then applies the following gates in order:

1. Read the live local QVAC model inventory and Hypha peer roster.
2. Reject stale peers, entries without a full executable provider key, and aliases that do not match the requested modality, minimum size, or specialist.
3. Enforce the sensitivity boundary before considering cost or speed.
4. Respect route intent: local, private, public, or automatic. For public candidates, additionally
   verify advert signature/TTL, tools, context, price, reachability, current load, memory headroom,
   and that requester and provider identities differ.
5. Rank deterministically and record the winning fields and reason. If the selected provider
   disappears, return the classified failure or follow the explicit automatic fallback policy;
   never label a local answer as remote success.

The mobile client uses the same live provider roster. It keeps its current provider while loads are equal and changes only when another eligible peer is genuinely less loaded, preventing roster-order flapping.

## Final public-compute measurements

The final warm benchmark completed all eight sequential jobs. Total latency was 1,013/1,047 ms
p50/p95; requester TTFT was 140/312 ms; provider TTFT was 111/214 ms; and throughput was
39.56/39.85 tok/s. Peak provider-system memory was 24,891 MB, below the 32 GB judging ceiling.

A four-request burst accepted one job and rejected three as `overloaded_provider`; it did not
silently run those requests locally. The normal web chat also completed a two-tool public turn as
two correlated remote QVAC jobs. Physical iPad and Android Release clients independently streamed
answers from the same unpaired Pro provider and displayed the public route evidence.

For the warm-cache offline check, the requester process was denied WAN access and the Pro's QVAC
inference serve was restarted under an outbound-network-denying macOS sandbox. The job still
completed over the signed public advert and direct LAN endpoint. The Hypha transport daemon was not
placed behind a host-wide firewall, so the evidence is intentionally described as process-level,
not a whole-host airplane-mode claim.

## Warm-peer overflow

The broker connects to the local Hypha service at `http://127.0.0.1:11437` by default. Set `LEASH_BROKER_HYPHA_URL` to an explicit empty value to disable mesh overflow. It can route a chat completion to a peer for two reasons:

| Trigger | Meaning |
| --- | --- |
| `availabilityRouted` | The alias is not served locally, but a peer has it warm. |
| `shed` | The local alias queue is already deep enough and a warm peer can take it. |

Overflow only targets a live peer that already holds the alias warm. It never pays a cold model load on the request path.

## KV-cache reuse, with proof

Delegated turns can reuse a peer's KV cache, but only when Hypha proves the request strictly extends the exact prefix already cached on that same peer.

QVAC custom KV keys are count-based, not content-addressed. A key hit sends only the turns beyond the stored count. If the prefix is wrong, the context is silently corrupt. So Leash uses a ledger:

| Case | Result |
| --- | --- |
| Same session, same peer, longer history, matching prefix hash | Reuse the generation key. |
| Edit, regenerate, peer switch, aborted turn, dirty entry, daemon restart | Bump generation and re-prime. |
| Ledger grows too large | Evict least-recently-used session; disk janitor sweeps later. |

Correctness beats speed. A faster wrong answer is not an optimisation.

## Identity and LAN fixes

Two mesh optimisations came from painful failure modes:

| Problem | Fix |
| --- | --- |
| Two HyperDHT servers using the same seed half-opened dials against the wrong process. | Only the SDK worker uses the raw seed; other swarms derive `sha256(seed + ":<role>")`. |
| HyperDHT's LAN shortcut could abort a same-public-IP dial without relay fallback. | Payment/control and mesh swarms force `localConnection:false` and holepunch instead. |

On a normal LAN, the forced holepunch path reconnects quickly and avoids the no-fallback LAN trap.

## Lazy mesh startup

Fresh daemons do not eagerly found separate meshes at boot. They run the local shim and pairing surface first, then found or join the Autobase at first pairing. This avoids the "two already-populated Autobases cannot merge" failure.

The design is less flashy than an always-on mesh, but it optimises for the thing users actually need: two devices can pair cleanly.

## Metered economy efficiency

The economy avoids per-token or per-chunk on-chain settlement. Metered sessions use an escalating Permit2 witness ladder and settle the highest reached rung once at close. Gas stays O(1) per session rather than scaling with token count.
