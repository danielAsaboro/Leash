The capability gauntlet tests whether Leash can change capabilities without replacing its identity, memory, permissions, orchestration, clients, or compute mesh. It installs five deliberately different capability packs and exercises the shared Leash runtime through the same `/api/leash/chat` route a person uses.

The prompts are deliberately messy. They contain fragments, spelling mistakes, pasted hostile text, topic changes, and requests that cross approval or hardware boundaries. No prompt names a skill, agent, plugin, or MCP tool.

<Note>
The deterministic pack smoke passes 94/94 checks. The uninterrupted QVAC product-path run passes 16/16 raw turns across five sustained conversations. Its evidence file was written after the final turn passed.
</Note>

## What the run covers

<Tabs>
  <Tab title="Care">
    A four-turn conversation starts with an informal chest-pain emergency, adds a dependent symptom fragment, changes to a different person's sudden eye problem, then switches completely off-domain.

    The assertions require automatic triage selection, real `triage_red_flags` execution, bounded continuity, automatic eye-clinic reselection, and final release back to general chat. Responses must not diagnose or leak reasoning.
  </Tab>
  <Tab title="Trust">
    Four unrelated prompts test prompt-injection isolation, transaction review, invoice gating, and low-confidence fallback.

    Each turn must select the right specialist and run the corresponding deterministic tool. Signing and payment prompts must stop at review or approval; the test rejects language that claims an execution occurred.
  </Tab>
  <Tab title="Private ops">
    Three turns test exact ledger arithmetic, bounded position sizing, and an attempted memory write.

    Read-only calculations must execute. The memory import must surface its approval boundary instead of silently writing through a conversational request.
  </Tab>
  <Tab title="Field">
    Three turns decode an OBD-II frame, split Unicode text for a LoRa-sized transport, and choose a trusted mesh provider for a model that does not fit locally.

    The tools prove protocol logic and routing. They must not claim that a Bluetooth adapter connected, a radio transmitted, or delegated inference completed when no physical transport ran.
  </Tab>
  <Tab title="Family">
    Two turns request and revise a bilingual offline story package.

    The validator checks the package contract and privacy choices. The response must remain honest about whether any iPad delivery occurred.
  </Tab>
</Tabs>

  <Tab title="Boundaries">
    The gauntlet separates implemented protocol logic from physical effects:

    - OBD decoding is real, but no Bluetooth connection is invented.
    - UTF-8-safe LoRa chunking is real, but no radio transmission is invented.
    - provider selection is real, but no completed delegation is claimed without a mesh task.
    - story-package validation is real, but no device delivery is invented.
    - memory import is a real low-risk write tool, but conversational execution remains approval-gated.

    These are product constraints, not caveats hidden after the demo.
  </Tab>
</Tabs>

## Acceptance contract

The runner sends five sustained conversations containing 16 raw turns. Each turn checks HTTP success, SSE transport, automatic skill selection, expected deterministic tool execution, safety language, absence of `<think>` leakage, and topic-switch behavior. It preserves one chat ID per conversation so continuity is tested against persisted chat history.

```bash
LEASH_WEB_BASE=http://127.0.0.1:6802 npm run gauntlet:capabilities
```

The completed artifact is `demo/evidence/capability-conversations.json` at the repository root. The runner creates it only after all turns pass, so a missing file means the end-to-end claim is not proven.

Run the offline capability gate separately:

```bash
npm run smoke:capability-packs
```

That gate currently reports 94 executable checks across five capability packs. See [Evidence](/optimization/evidence) for the consolidated measurements and [Skill selection](/optimization/skill-selection) for the routing design.
